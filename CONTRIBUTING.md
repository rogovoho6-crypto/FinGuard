# Как команда работает с FinGuard

`main` — общая проверенная версия. Одна задача = одна отдельная ветка = один Pull Request (PR). PR — предложение добавить вашу работу в main с просмотром изменений и проверками.

## 1. Первый запуск участника

Владелец приглашает GitHub-пользователя через Settings → Collaborators / Manage access; участник принимает приглашение. Пароль от аккаунта владельца передавать не нужно. Приглашения отправляет владелец выбранным участникам.

Установите Git и запущенный Docker Desktop. В GitHub нажмите Code → HTTPS и скопируйте настоящий адрес репозитория:

```powershell
git clone https://github.com/rogovoho6-crypto/FinGuard.git
cd FinGuard
git config user.name "Ваше имя"
git config user.email "Ваш GitHub email или noreply из Settings → Emails"
.\02_develop.bat
```

Угловые скобки обозначают места для подстановки, вводить их буквально не нужно. При запросе входа используйте браузерную авторизацию Git Credential Manager. Обычный пароль аккаунта GitHub не служит паролем git push; не присылайте токены в чат.

Приложение: http://localhost:5173. Каждый работает со своей локальной базой. `.env` для обычного режима создаётся локально через 00_prepare.bat и не попадает в Git.

## 2. Начать новую задачу

Убедитесь, что `git status` не показывает незавершённых изменений предыдущей задачи.

```powershell
git switch main
git pull --ff-only origin main
git switch -c feature/payment-filter
```

Названия: `feature/название` для функции, `fix/название` для ошибки, `docs/название` для инструкции. Пишите латиницей, например `fix/scenario-date`. Не создавайте всем одну ветку develop: для небольшой команды достаточно main и веток задач.

## 3. Изменить, проверить, отправить

```powershell
git status
git diff
```

Внесите изменения в редакторе. Для frontend/src и backend работает обновление без пересборки. Для новых зависимостей повторите 02_develop.bat. Запустите 05_test.bat; ожидается OK.

Добавляйте именно файлы своей задачи, например:

```powershell
git add frontend/src/pages/Payments.tsx
git diff --cached
git commit -m "Add payment filter"
git push -u origin feature/payment-filter
```

Если меняли несколько файлов, перечислите их через пробел. Перед commit проверьте `git diff --cached`. Не добавляйте .env, SQLite-копии, реальные платёжные файлы или токены. .gitignore снижает риск, но не проверяет все данные внутри документов.

## 4. Создать Pull Request

На GitHub откройте Compare & pull request для своей ветки. Base: main; compare: ваша ветка. Заполните подготовленный шаблон: что изменено, как проверить, результаты. Назначьте одного участника на review. Большие незавершённые задачи открывайте как Draft PR.

GitHub Actions после загрузки выполнит Docker-сборку frontend и 89 тестов. Вкладка Checks показывает результат. Если проверка упала, откройте её журнал, исправьте ошибку и сделайте новый commit/push в ту же ветку: PR обновится сам.

## 5. Проверка и объединение

Проверяющий читает Files changed, проверяет результат и оставляет замечания или Approve. Автор исправляет замечания в своей ветке. Когда Checks зелёные и review получен, ответственный выбирает Squash and merge. Так в main появляется один понятный commit на задачу. Затем можно Delete branch на GitHub.

Сам по себе зелёный CI не означает, что функция удобна или верна: проверьте пользовательский сценарий. Не объединяйте финансовую логику без числового примера и соответствующего теста.

## 6. После объединения

```powershell
git switch main
git pull --ff-only origin main
git fetch --prune
```

Следующую задачу начинайте новой веткой от обновлённой main. Старую локальную ветку можно оставить; удалять её для продолжения работы не обязательно.

## 7. Если main изменилась, пока вы работали

Сначала сохраните свою работу commit-ом в своей ветке. Затем:

```powershell
git fetch origin
git merge origin/main
```

При конфликте Git укажет файлы. В редакторе сопоставьте обе версии, оставьте нужный итоговый код и уберите маркеры `<<<<<<<`, `=======`, `>>>>>>>`. Не выбирайте «принять всё» без чтения.

```powershell
git add <ИСПРАВЛЕННЫЕ_ФАЙЛЫ>
git commit -m "Merge main and resolve conflicts"
git push
```

Снова проверьте приложение и тесты. Если не готовы решать конфликт, `git merge --abort` отменяет незавершённое слияние; поэтому до merge требовалась чистая рабочая папка. Не используйте force push или reset --hard как стандартное исправление проблемы.

## 8. Правила владельца

В Settings → Rules / Branches настройте main: Pull Request, один approval, закрытые обсуждения и успешный check `Docker build and 89 tests`; запретите force push и удаление main. Сначала дождитесь первого CI-запуска, чтобы check появился в списке.

Репозиторий открыт для жюри. Публичный доступ позволяет читать код и скачивать проект; права записи остаются у владельца и добавленных участников. Наличие файла CI не означает, что защита main включена: владелец проверяет правила в Settings отдельно. Работайте через ветки и Pull Request, проверяйте CI перед объединением.

Настройте Squash merging и автоматическое удаление объединённых веток, если они доступны. Для хакатона назначьте одного человека ответственным за merge. Не публикуйте обновление на внешний сервер автоматически: текущий workflow только собирает и тестирует.

## 9. Отличия Docker и Git

Git передаёт код. Docker запускает код в одинаковом окружении. Git pull не переносит чужую базу и не пересобирает автоматически обычную версию: для неё выполните 01_start.bat. Режим разработки подхватит код сам; после изменения зависимостей повторите 02_develop.bat.
